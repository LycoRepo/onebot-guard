# 技术栈与语言选择

这个项目实际只有一个 Node.js 服务运行时。GitHub 显示的多个语言分类，分别覆盖服务逻辑、浏览器界面和容器部署，并不代表维护五套后端。

## 每种文件在做什么

| 分类 | 所在位置 | 用途 | 是否可以合并 |
| --- | --- | --- | --- |
| TypeScript | `src/**/*.ts`、`tests/**/*.ts` | 协议网关、鉴权、策略、HTTP 接口、测试 | 核心业务已经统一使用 TypeScript |
| JavaScript | `src/webui/static/app.js`，登录页内嵌脚本 | 浏览器交互、草稿、状态轮询、SSE 日志 | 可改写为 TS，但需要生成浏览器可执行的 JS |
| HTML | `src/webui/static/index.html`、`login.html` | 页面结构、表单与无障碍语义 | 即使用框架，也仍需输出 HTML |
| CSS | `src/webui/static/style.css`，登录页内嵌样式 | 配色、布局、响应式、控件状态 | 不适合为了减少语言分类而移除 |
| Dockerfile | 仓库根目录 | 把 Node 服务和静态资源打包为镜像 | 是部署描述，不是另一套业务语言 |
| YAML / JSON | 配置、Compose、package.json、tsconfig.json | 策略数据、编排、依赖与工具配置 | 这些是配置格式，不是额外服务 |

## 为什么后端 TS、前端 JS

项目要求 Node >= 24，后端通过 Node 的类型剥离执行 TypeScript；`tsc --noEmit` 单独负责类型检查。浏览器执行的仍是 JavaScript，因此目前将前端写成普通 JS，直接由 WebUI 服务读取并提供。

这样只需要 `ws` 和 `yaml` 两个直接运行依赖，没有前端框架、打包器、CDN 或前端构建产物。登录页内嵌的脚本与样式由服务端计算 CSP 哈希；主面板静态资源通过认证后访问。

若把前端改成 TypeScript，会改善编译期检查，但必须增加输出 JS 的步骤，并同步修改镜像构建、静态资源路由、测试与发布流程。TS 并不能代替 HTML 和 CSS，因此语言栏不会因此只剩一种语言。

## 真正的维护成本在哪里

当前 `app.js` 集中了 API 访问、草稿模型、端点和路由表单、规则、日志、页面导航。多个页面共享配置，却采用不同的保存与生效方式，这比文件扩展名的数量更容易引入问题。

本次改版集中处理这些实际问题：

- 概览增加链路状态与三步配置入口，明确连接、就绪和转发的区别。
- 端点/路由草稿可以撤销；规则和 YAML 也保护未保存编辑。
- 修复最后一条路由删除时的脏状态漏报、删除端点保存后错误留在草稿基线、只读控件仍可操作的问题。
- 路由配置与实际运行状态同时可见。
- 规则支持多策略选择，切换失败保留当前编辑；规则和 YAML 保存后同步，互有未保存修改时阻止覆盖。
- 保存非策略配置后显示待重启状态，并在刷新后重新与运行配置比较；策略保存不再让用户盲目重试。
- 日志提供路由信息、类型筛选和搜索；保留原有容量上限。

本次没有增加依赖或新的语言，也没有将网关迁移到其他技术栈。

## 后续规模扩大时如何选择

优先把浏览器代码按 API、草稿状态、端点、路由、规则、日志拆分为原生 ES modules，并同步维护静态资源白名单和测试。若编辑器与多人协作需求继续增长，再考虑前端 TypeScript 和组件框架；引入它们的理由应是状态复杂度和维护收益，而不是让 GitHub 的语言栏更短。

## 本次验证

- Node 24.22.1，TypeScript 类型检查通过。
- 88 项自动测试：87 通过；Windows 上跳过 1 项 Unix SIGHUP/SIGTERM 测试。
- 本机真实 HTTP/WebSocket 演示网关与 Edge 无头浏览器：登录、跨页草稿、保存、撤销、策略选择、规则保存与 YAML 同步、刷新后待重启提示、日志筛选通过。
- 1536、1024、768、390 像素四种视口下检查六个页面，未发现整页横向溢出；无浏览器脚本错误。

浏览器验证使用临时模拟协议端，不代表真实 QQ 协议端的生产兼容性验证。配置撤销只覆盖当前浏览器草稿，不是持久化历史回滚；当前也没有跨浏览器编辑冲突检测。
